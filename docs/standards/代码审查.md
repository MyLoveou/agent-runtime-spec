# 代码审查

> 状态：**样板** —— 复制到业务仓后，按 `{...}` 填本项目的真实路径
> 关联：`skills/code-review-gate/SKILL.md` · `rules/common-code-review`

## 1. 目的与时机

代码审查用于在合并或交付前发现质量、安全与规格偏差。以下场景**必须**审查：

| 场景 | 说明 |
|------|------|
| 功能改动完成 | Agent 或开发者交付前 |
| 用户明确要求 | 「审查」「review」「合并前看看」 |
| 跨层 / 持久化 / IPC | 领域 + 主进程 + 前端要一起审 |
| 安全敏感 | auth、用户输入边界、文件路径、密钥 |

审查通过后，再进入 Bugbot（平台提供时，可选）与 `verification-gate`（构建、测试、手测）。

完整流水线见 [工作流索引.md](./工作流索引.md)。

## 3. 严重度与裁决

| 级别 | 含义 | 动作 |
|------|------|------|
| **CRITICAL** | 安全漏洞、数据丢失、密钥泄露 | **BLOCK** — 必须修复 |
| **HIGH** | 功能错误、规格明确违背、数据丢失风险 | **WARN** — 合并/交付前应修复 |
| **MEDIUM** | 可维护性、错误码、测试缺口 | **INFO** — 建议修复 |
| **LOW** | 样式细节、文档滞后 | **NOTE** — 可选 |
| **INFO** | 计划内未实现（Phase 边界） | 记入 backlog，不阻塞 Phase 内交付 |

**裁决：**

- **Approve**：无 CRITICAL / HIGH
- **Warning**：仅有 HIGH（可谨慎合并，须跟踪修复）
- **Block**：存在 CRITICAL

## 4. 通用必查项

- [ ] 符合 `docs/requirements/features/<能力>/需求.md` 与已定稿的实现方案
- [ ] 接口与 `{API_DOC}` 一致
- [ ] 边界校验在服务端 / 主进程完成，前端不假设输入可信
- [ ] 无密钥、`.env`、`{LOCAL_DB_PATH}` 误提交
- [ ] 不可变数据：store / patch 不原地 mutate
- [ ] 新能力有对应测试；核心模块行覆盖 ≥ 80%
- [ ] 用户可见错误有 toast + 可读文案（非裸 stack）
- [ ] 改 `{HOT_PATH}` → 对照 `{PERF_SPEC}`（无 N+1、无重复读）
- [ ] 改 `{CRITICAL_PATH}` → `{BENCH_CMD}` 无新增 fail

## 6. 审查输出模板

```markdown
## 审查结果 · <能力/模块> · <日期>

**裁决：** Approve / Warning / Block

### 摘要
（2–3 句）

### 发现
| 严重度 | 文件 | 问题 | 建议 |
|--------|------|------|------|

### 待修复（HIGH+）
- [ ] …

### 是否可进入 verification-gate
是 / 否
```

审查记录归档：写入对应领域规范或 PR 描述。

## 7. 与 Bugbot、verification-gate 分工

| 环节 | 职责 |
|------|------|
| [TDD与测试.md](./TDD与测试.md) | RED→GREEN→REFACTOR；覆盖率 ≥ 80% |
| code-review-gate（本文） | 质量、规格、安全 |
| [Bugbot审查.md](./Bugbot审查.md) | diff 回归、静默 bug |
| verification-gate | `{LINT_CMD}` · `{TEST_CMD}` · `{BUILD_CMD}` · 手测 |

**推荐顺序：** TDD → code-review → Bugbot → verification-gate

有 BLOCKER → 先修再进入下一环节。
