# 多仓协同

> 一次改动要落到多个仓（导出资产、迁笔记、发版）时走这条。单仓改动不需要。

## 何时用

- 改了本库资产，需要同步到多个业务仓；
- 多个仓同时有未提交改动，要先判断能不能动；
- 经验总结要从项目本地搬到 temp；
- 一次发布涉及本库 + 多个业务仓的版本。

## 步骤

| # | 步骤 | 用什么 | 产出 | 门禁 |
|---|---|---|---|---|
| 1 | 巡检 | `repo-surveyor`（只读） | 各仓状态表 | 有脱管 / 脏仓先标红 |
| 2 | 定范围 | `planner` | 这次动哪几个仓、顺序 | 用户确认 |
| 3 | 导出 | `exporter` | 逐仓报 copied/same/diff | 不加 `-Force`；diff 需说明 |
| 4 | 笔记 | `note-curator` | 新增 / 合并 / 迁移清单 | 先搜后写，无重复条目 |
| 5 | 本库发布 | `verification-gate` → 分支 → 合并 → tag | 版本 + tag + CI | `spec-check` 绿 |
| 6 | 业务仓收尾 | 各仓自己 commit / push | 每仓独立提交 | 不代用户提交别人的 WIP |

## 并行与串行

- 步骤 1 与 4 可并行（都是只读或只动 temp）；
- 步骤 3 必须串行：一仓失败就停，不继续下一仓；
- 步骤 5 与 6 互不阻塞：本库发版不依赖业务仓提交。

## 失败分支

| 现象 | 退回 |
|---|---|
| 巡检发现有仓脱管（HEAD） | 停下，先让用户决定是否回分支 |
| 某仓脏文件很多 | 只读、不改；把差异列出来 |
| dry-run 出现 diff | 报告哪些文件会被覆盖，等确认 |
| 导出后目标侧数量不符 | 回步骤 3，查装配单是否漏项 |
| temp 历史分叉 | 先合流再继续（参考 D-20261108-09） |

## 验收

- [ ] 每个被改的仓都有独立的「改了什么 / 提交 / 是否推送」记录
- [ ] 本库闸门全绿，CI success
- [ ] temp 的改动已提交并推送（它是共享 clone）
- [ ] 没有把别人的未完成提交一起推出去
