# 技术可行性调研

给候选需求补一份**可落地的判断**，不做实现。

## 输入

- 候选卡（来自 `market-scout`）
- 目标仓：技术栈、现有依赖、构建与测试方式
- 可用手段：`search-first`（先搜仓库与现成方案）

## 每份评估回答五件事

| 问题 | 判据 |
|---|---|
| 现有依赖够不够 | 版本、是否已在用、能否复用 |
| 要引入什么 | 包名 + 许可 + 最近更新 + 体积 |
| 集成点在哪 | 具体文件/模块，不改架构能否接 |
| 工作量 | S（≤1 天）/ M（2–3 天）/ L（>3 天） |
| 风险 | 数据迁移、兼容性、性能、许可、维护活跃度 |

## 输出

```markdown
### 技术评估：<候选名>

- 结论：可行 / 有条件可行 / 不可行
- 依赖：<已有 / 新增 <包>（<许可>，更新于 <年-月>）>
- 集成点：<文件或模块>
- 工作量：<S/M/L>（依据：<改哪几处>）
- 主要风险：<...>
- 替代方案：<不引入新依赖的做法，若有>
```

## 红线

- 不装包、不改 `package.json` / `pyproject.toml`、不写代码；
- 不把「搜到过」当成「验证过」——没跑过的写「未验证」；
- 许可不明（NONE / NOASSERTION）的依赖一律标红。

## 交接

- 评估回到根代理，与候选卡合并后进评审门；
- 批准后由开发代理实现，评估里给的文件定位就是开工入口。
