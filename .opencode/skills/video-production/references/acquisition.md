# 素材获取：元数据与视频

> 两类素材：**条目元数据（书名/封面/简介）** 与 **视频素材（B-roll / 背景）**。两者都有「先探测再批量」的纪律。

## 一、条目元数据采集

### 需要什么能力

- 按标题列表批量查询平台；
- 拿详情：简介、作者、字数、连载状态、封面 URL；
- 标题相似度匹配（平台返回常有多条候选）；
- 把结果落成结构化 JSON（原始文件不覆盖）。

### 平台特性（2026-11 核对，易变）

| 平台 | 搜索 | 详情 | 备注 |
|------|------|------|------|
| 番茄 | 每次约 10 条/词，**不带字数** | 有简介、字数、状态 | 详情字段名是 `intro` 不是 `abstract` |
| 起点 | 约 20 条，噪声大 | 可用 | 标题匹配易误伤 |
| 刺猬猫 | 搜索接口有风控，常返回 0 / 5xx | 详情页可访问 | 搜索不可用时按 ID 抓详情 |

### 匹配策略

- 相似度 ≥ 0.85 自动接受；否则标 `needs_review` 并存候选，人工选；
- 同一条目多平台都有时，按「起点 → 番茄 → 刺猬猫」取第一个高分；
- **标题会变**：同一本书在不同期/不同平台会改标题。稳妥做法是**存平台链接/ID**，按 ID 抓详情，不靠标题。

### 采集后清洗

原始简介常见脏内容：开头标签块（`【XX同人+无系统】`）、作者注（「因为作者…」）、求票尾巴、章节提示（「（45 章揭示真相）」）。

清洗原则：**只删非情节内容，不改写情节**；输出新文件，原始 JSON 保留（可回溯、可重跑）。

### 已知缺陷

- 某些平台的「连载/完结」状态字段语义与直觉相反（例如 `1` = 连载中），接入新平台时先用 2–3 本人工核对，别信字段名。

## 二、视频素材下载

### 铁律：先探测，再下载

同一支视频，A 平台可能把字幕**烧进画面**，B 平台是**独立字幕轨**（画面无字）。不探测就批量下，会白下几个 GB。

探测看三件事：

1. 时长 / 最高分辨率；
2. 流结构：只有 `video + audio` 两条流 → **硬字幕**（烧进画面）；有独立 `subtitles` 轨 → **软字幕**，画面本身无字；
3. 是否需要登录态（高清 / 4K 常需要）。

### 下载能力要求

| 能力 | 为什么需要 |
|------|------------|
| 浏览器登录态复用 | 避免手工导出 cookie |
| JS 挑战求解 | 新版下载器缺 JS 运行时会对高清报 `n challenge solving failed` |
| 代理 | 部分地区/站点需要 |
| 不取字幕 | 需要无字画面时默认不下载字幕 |

### 硬字幕的处置顺序

1. **找无字源**（同片官方版 / 其他平台）——代价最小，首选；
2. 裁切（切掉底部字幕带）——会切构图；
3. 遮盖（同色条 / 模糊条）——有痕迹；
4. 逐帧 AI 修补——极慢，运动镜头糊，不建议整段。

### 平台差异

- 合集/系列要按 API 取（`series_id` 之类），不要一页页翻；
- 多分 P 常是多语言版本（p1 中文 / p2 日语 …）——只下需要的那一 P；
- 高清、4K、60fps 需要更高权限。

## 三、版权与留痕

- 官方素材用于同人向二次创作是常见做法，但**未获授权**；商用、原样搬运有风险；
- 素材下载后在 `相关/链接.md` 记录来源 URL、下载日期、用途；
- 不存账号、cookie、密钥进项目目录。

## 四、验收

- [ ] 每个条目都有：标题、作者、字数、状态、简介、封面
- [ ] 原始 + 清洗两份 JSON 都在
- [ ] 封面文件与条目一一对应，无缺图
- [ ] 视频素材已确认无硬字幕（或已按上面顺序处理）
- [ ] 来源链接已留痕
