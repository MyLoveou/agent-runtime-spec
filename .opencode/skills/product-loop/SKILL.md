# 产品迭代循环

## 何时用

- 用户明确说「你自己找需求、安排实现，持续做」；
- 有多个小需求可以按轮次推进；
- 团队里有子代理可以并行（调研 / 开发 / 审查分工）。

**没有用户明确授权时不要启动**；没有评审门时不要连续改需求。

## 角色

| 角色 | 谁 | 产出 | 边界 |
|---|---|---|---|
| 市场调研 | `market-scout` | 需求候选卡（用户痛点、竞品做法、证据） | 只读，不改代码 |
| 技术调研 | `tech-scout` | 可行性（依赖、许可、成熟度、工作量） | 只读，不改代码 |
| 开发 | 现有 dev agent（backend-dev / frontend-dev / …） | 分支上的改动 | 只在自己的分支 |
| 审查 | `code-reviewer` | 审查意见 | 不改代码 |
| 门禁 | `verification-gate` | 通过/阻塞 | — |
| 记账 | `note-curator` / `knowledge-extract` | 经验、决策、事实更新 | 只写 temp 与文档 |

根代理只做编排：派活、收结果、过评审门、合并。

## 一轮循环（七步）

| # | 步骤 | 门禁 |
|---|---|---|
| 1 | 调研：市场 + 技术各出一份 | 两份都有证据来源才进入 2 |
| 2 | 合成候选卡（≤3 个） | 每个都要有「不做的代价」 |
| 3 | **评审门：交用户批准** | **未批准不进入 4** |
| 4 | 切分支 `feat/<需求>`，派开发 | 不直推 master |
| 5 | 闸门：构建 / 测试 / 审查 / 验收 | 任一红就修，修不好停 |
| 6 | 合并 → 记账（facts / decisions / handoff / 经验） | 合并前再跑一次闸门 |
| 7 | 回到 1，带上「上轮遗留」与「用户否决理由」 | 预算耗尽则停 |

## 评审门的候选卡格式

```markdown
### 候选 <N>：<一句话>

- 用户痛点：<谁、什么场景、现在怎么凑合>
- 证据：<链接/数据/用户原话>（没有证据就写「假设」）
- 竞品做法：<谁做了、做到什么程度>
- 我们怎么做：<最小可行形态，一句话>
- 不做的代价：<会错过什么>
- 成本：<S/M/L>　风险：<低/中/高>
- 建议：做 / 缓 / 不做（给理由）
```

用户回复可以是：`1、3 做`、`全部缓`、`候选 2 换个做法`——**未明确回复即视为未批准**。

## 分支纪律

- 一个需求一条分支，从最新 master 切；
- 合并前必须：闸门绿 + 审查无阻塞 + 用户已批准该需求；
- 冲突在分支里解（rebase），不把冲突带到 master；
- 合并后删分支，不留长命分支。

## 预算与停止条件

| 项 | 默认 |
|---|---|
| 每轮候选数 | ≤3 |
| 单需求改动 | ≤15 文件；超了就拆 |
| 单需求尝试次数 | 2 次；第 2 次仍红 → 停 |
| 连续失败 | 2 轮 → 停，报告 |
| 每轮结束 | 必须回报：做了什么、绿的证据、下一步候选 |

**停止条件**：用户中断 / 评审门未过 / 连续失败 2 次 / 预算耗尽。除这四种，不要自己停。

## 记账

| 记什么 | 写哪 |
|---|---|
| 需求与取舍 | `docs/product/decisions.md`（一条一决策） |
| 项目现状变化 | `docs/product/facts.md` |
| 跨轮进度 | `handoff.md` 或 `docs/HANDOFF.md` |
| 可复用的坑与原理 | `temp/经验总结/<项目>/` |

## 反模式

| 不要 | 为什么 |
|---|---|
| 自己批准自己的需求 | 评审门是唯一的人工闸 |
| 一轮塞 10 个需求 | 无法验收，也无法回滚 |
| 改完不记 decisions | 下一轮会重复讨论 |
| 直推 master | 出问题无法定点回滚 |
| 「我感觉这个功能很好」 | 候选卡必须有证据或明确标为假设 |
